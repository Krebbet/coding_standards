# Project Flow

## Project Start

1. **Repo Setup:** A Github repo will be set up by the project manager with appropriate permissions for relevant team members, branch protections, etc to reflect the SFL Scientific ways of working. See  ‣ 
    1. SFL repos should be built off of a common template to try to standardize the code layout. 
    2. The repo provided should already mirror the Template: [https://github.com/Deloitte-US-Consulting/SFL-Template](https://github.com/Deloitte-US-Consulting/SFL-Template)
    3. You should definitely make it project-relevant, so please remove folders that aren't applicable and alter structure as it makes sense.
2. **Set Up Working Environment:** The development team should clone this repo to their working environment (company laptop, client cloud resource, etc). 
3. **Customize Project Framework:** The development team should customize the template framework as needed for the project. This should be done on a branch of the project and submitted for a PR as early as possible in the project so the entire development team is working off of the same framework. 
4. **Set Up Docker Image:** For ease of delivery at the end of a project, a docker image should be set up at the start of a project. All development should take place within the docker. If you are unfamiliar, see the [Docker Quickstart](https://www.notion.so/Docker-Quickstart-7a42c5a7eb1b4f44951c81d551083d42?pvs=21).

## During Project

1. **Branch:** Create development branches that accurately describe and encompass the features that are being developed. 
2. **Commit:** Commits should be small and happening regularly. Plan to commit changes 2-3x per day.
3. **Push to Remote:** Push to Github at minimum once every 2 days. If you get hit by a bus, another SFL Scientific member will only have to replicate at most 2 days of work. I*t is recommended that you make sure all git actions pass when pushing to remote.*
4. **Standardize Before PR:** Make sure code follows our [Writing Code](../Writing%20Code%20a80c65f8b839461797206892831889f6.md) and that *all git actions pass*.
5. **Pull Request to Merge:** Merge a development branch with a completed feature into the master branch using a pull request. Make sure 2 reviewers are assigned. 
6. **Code Review:** Code must be reviewed and approved by 2 reviewers in order to merge and close a pull request.
