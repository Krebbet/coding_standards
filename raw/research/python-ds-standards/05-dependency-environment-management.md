## Why This Is Hard in Data Science

Data science projects are unusually dependency-heavy. A single project may combine CUDA-compiled packages (PyTorch, CuPy), conda-distributed binaries (GDAL, RAPIDS), and pure-Python packages from PyPI. Getting reproducible environments across developer machines, CI, and production is a known friction point.

## The Two-File Pattern for pip-Based Projects

Do not commit a flat `requirements.txt` generated by `pip freeze`. It conflates your direct dependencies with transitive ones, making upgrades fragile and maintenance opaque.

Use **pip-tools** or **uv** to separate abstract and concrete requirements:

- `requirements.in` — your direct dependencies with loose version constraints
- `requirements.txt` — the fully pinned lockfile generated from `.in`, committed to the repo
- `requirements-dev.in` / `requirements-dev.txt` — development-only dependencies (pytest, black, ruff, etc.)

```
# requirements.in
pandas>=2.0
scikit-learn>=1.4
matplotlib
```

```bash
pip-compile requirements.in        # generates requirements.txt with pinned hashes
pip-compile requirements-dev.in
pip-sync requirements.txt requirements-dev.txt   # installs exactly the pinned set
```

## Poetry for Pure-Python Projects

Poetry is the cleanest solution for projects that do not require conda. It manages a `pyproject.toml` (abstract deps) and `poetry.lock` (exact pins) in one tool:

```bash
poetry add pandas scikit-learn         # adds to pyproject.toml and updates lock
poetry add --group dev pytest ruff     # dev-only deps
poetry install --sync                  # installs exactly what the lockfile specifies
```

Commit `poetry.lock`. Do not `.gitignore` it — it is what makes other developers' environments match yours.

## Conda for Mixed Binary/Python Environments

Use conda (or mamba for speed) when your stack includes packages that must be compiled against system libraries — geospatial tools, GPU libraries, or packages with non-trivial C extensions that PyPI wheels do not cover reliably.

Export environments two ways:

```bash
# Exact cross-platform lockfile (for CI/other devs on the same OS)
conda list --explicit > conda-lock.txt

# Cross-platform abstract spec (for human review and cross-OS recreation)
conda env export --from-history > environment.yml
```

In practice, many teams use conda for system-level dependencies and pip/Poetry for the Python package layer on top, defined in a single `environment.yml`:

```yaml
name: my-project
channels:
  - conda-forge
  - defaults
dependencies:
  - python=3.11
  - cudatoolkit=11.8
  - pip
  - pip:
    - -r requirements.txt
```

## uv: Fast Modern Alternative

**uv** (from Astral, the makers of ruff) is a drop-in replacement for pip and pip-tools written in Rust, with dramatically faster resolution and install times. For new projects not requiring conda, it is worth adopting:

```bash
uv venv .venv
uv pip compile requirements.in -o requirements.txt
uv pip sync requirements.txt
```

## Key Practices Regardless of Tool

**Always pin in CI and production.** Abstract dependencies (`pandas>=2.0`) are fine in `pyproject.toml` for human readability; the lockfile with exact pins is what should be installed in automated environments.

**Isolate every project.** Never install project dependencies into the system Python. Use `python -m venv .venv`, a conda environment, or Poetry's managed venv. Add `.venv/` to `.gitignore`.

**Document the Python version.** Specify the Python version in `.python-version` (for pyenv), `pyproject.toml`, and your CI configuration. Version mismatches between local and CI are a common source of confusing failures.

**Separate runtime and development dependencies.** Testing frameworks, formatters, and notebook servers should not be installed in production images. Keep `dev` and `runtime` dependency groups distinct.

**Review lockfile diffs in pull requests.** Changes to `poetry.lock` or `requirements.txt` are meaningful — they may introduce new transitive dependencies or version bumps that break things. Treat them as code, not noise.
