# MLOps Principles and Feature Engineering as Software

MLOps is the discipline of applying DevOps principles — automation, continuous delivery, monitoring — to the ML model lifecycle. It treats model training and deployment as a software engineering problem, not a one-off research task.

## The Three Levels of MLOps Maturity

Google's MLOps whitepaper defines three maturity levels that provide a useful roadmap:

**Level 0 — Manual process**: data scientists train models manually, deliver a frozen model artefact to engineering for deployment. No pipeline automation, no CI/CD for models, retraining is manual and infrequent. Appropriate only for very early-stage or low-stakes systems.

**Level 1 — ML pipeline automation**: the training pipeline is automated and can be triggered on a schedule or by data drift detection. Feature engineering is part of the pipeline, not a separate notebook. Models are retrained continuously, but pipeline development is still manual.

**Level 2 — CI/CD pipeline automation**: changes to pipeline code trigger automated build, test, and deployment of new pipeline versions. A change to a feature transform goes through the same CI/CD process as a change to a web service. This is the target state for any system where model quality affects business outcomes.

Most teams should aim for Level 1 before pursuing Level 2 infrastructure.

## Continuous Training

Unlike traditional software where a deployed version is stable until explicitly changed, ML models decay as the world changes. Continuous training is the practice of regularly retraining on fresh data:

- Define a **retraining trigger**: time-based (weekly), volume-based (every N new examples), or drift-based (when KL divergence between live and training distributions exceeds a threshold).
- Automate the full pipeline so retraining requires no human intervention for the happy path.
- Gate automated promotion on automated evaluation: the new model must beat the current production model on a fixed evaluation set before it can be deployed.

## Feature Engineering as Software

Feature engineering is the highest-leverage part of most ML pipelines, and it is frequently the most poorly engineered. Principles:

**Encapsulate transforms in functions, not notebooks.** Every feature transform should be a pure function: input data → output data, no side effects, no global state. This makes it testable, reusable, and debuggable.

**Separate feature computation from feature retrieval.** Compute features once, store them, and retrieve them at training and serving time from the same store. Computing features differently in training and serving is the root cause of training-serving skew, one of the most common and costly ML production bugs.

**Version feature sets explicitly.** A "feature set" is a named, versioned collection of features used to train a model. When the feature set changes, the version increments. The model is always tied to a specific feature set version, not to "the latest features."

**Document the business meaning of every feature.** A column named `f_42` or `user_emb_dim_7` is a liability. Every feature should have a name that communicates what it measures, a description of how it is computed, the unit or range of its values, and any known issues or caveats.

## Monitoring in Production

A deployed model has two kinds of health:

- **System health**: latency, error rate, throughput. Monitor with standard infrastructure tooling (Datadog, Prometheus).
- **Model health**: prediction distribution drift, feature distribution drift, label drift (if labels are available with a lag), business metric degradation.

The simplest effective monitoring setup:
1. Log every prediction with its input features (sampled if volume is high).
2. Compute daily summary statistics on feature distributions and compare to training baseline.
3. Alert when any feature's PSI (Population Stability Index) exceeds 0.2, or when prediction distribution mean shifts by more than 2 standard deviations from baseline.
4. Where ground truth labels are eventually available, compute rolling model performance and alert on degradation.

## Dependency and Environment Management

- Pin all dependencies to **exact versions** in production training jobs. `scikit-learn>=1.0` will eventually resolve to a version that changes default behaviour and silently degrades your model.
- Use a **single requirements lock file** generated by `pip-compile` or `poetry lock`. Commit it to version control. Reproduce the training environment from it in CI.
- Use **Docker images** with pinned base images for training jobs. The image digest (not just the tag) should be logged with each experiment run.
